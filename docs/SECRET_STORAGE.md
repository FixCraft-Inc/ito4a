# Transport configuration storage

Ito owns this store. It stores manual configurations independently of Android
preferences and other applications. libyume opens sealed documents and validates
the client configuration and credential files before the importer publishes them.
An imported configuration is not selected automatically. Connecting uses the
explicitly selected configuration, with no substitute after a failure.

## Encrypted snapshot

`ConfigurationStore` stores one authenticated encrypted snapshot beneath
`Context.noBackupFilesDir/ito-transport/`. It includes the catalog, selected ID,
and credential files. Each operation decrypts a private candidate, validates it,
and clears its owned byte arrays when the operation returns. Public catalog
results contain only random IDs and user labels. They contain no credential
material, native configuration or disk paths.

The Android Keystore holds a non-exportable AES-256 key under the app's own
alias. AES/GCM/NoPadding uses a fresh 96-bit nonce generated by the platform
cipher and a 128-bit authentication tag. An application-format version and domain
are authenticated as additional data. This protects app data at rest and is separate
from YUME transport cryptography. Buffer clearing is best effort and does not
erase VM/provider copies, flash blocks or a compromised process's memory.

There are at most eight configurations, 2 MiB per configuration, 12 MiB of
combined material, 32 files per configuration and 1 MiB per file. Relative file
paths contain only bounded ASCII components. Empty components, traversal,
absolute paths, links and special files are refused. Every bundle contains
`yume.json`. Labels are bounded nonempty display text. They confer no authority.

The manifest excludes application data from cloud backup and device transfer,
and `allowBackup` and legacy full backup are disabled. Secret files additionally
live under `noBackupFilesDir`. The store does not export keys or a recovery
password. Reinstalling the app or losing its Keystore key makes retained
ciphertext unreadable. It is not safe to restore ciphertext into another app
installation and assume it can be opened.

## Publication and recovery

Mutations hold one in-process monitor. They read and authenticate the current
snapshot before creating a replacement. The complete new ciphertext is written
to a private temporary file, synced, and atomically renamed over the snapshot.
This is a single-file atomic replacement. It does not promise persistence across
loss of storage or power before the filesystem commits its directory metadata.
An interruption before rename leaves the old snapshot. An interruption after
rename leaves the new complete snapshot. Startup removes only the store's named
temporary file. It never promotes an unauthenticated temporary candidate.

A corrupt, oversized, unsupported, unreadable or unauthenticated snapshot fails
closed with a typed error. The existing bytes remain in place. Import, selection
and removal cannot overwrite that state. An existing snapshot with an absent,
invalidated, locked or unavailable Keystore key reports `KeyUnavailable` and
never creates a replacement key. The app must show the failure and preserve the
data. Recovery requires the user to remove this app's data through Android and
reimport fresh source documents. There is no silent repair, default catalog or
fallback to a different configuration. A missing snapshot is an empty catalog,
but a leftover inaccessible key does not authorize overriding ciphertext.

Deletion is an authenticated local snapshot mutation and works offline. Deleting
the selected entry clears selection. It preserves every other entry. It removes
the configuration from the current snapshot, but cannot erase prior ciphertext
blocks or external source documents. Uninstall/data clearing removes the app's
store and Keystore entry through Android. No remote revocation is inferred from
local deletion.

## Plaintext lifetime

Import reads the document with a strict size bound, opens it through the public
native API and stages credential files only inside the app's no-backup
directory. Cancellation observed at the import publication checkpoint leaves the
catalog unchanged. Opening a stored configuration creates a uniquely named
private session directory. It writes only validated relative files with exclusive
creation. Callers hold a
`ConfigurationSession` while JNI borrows its files and close native handles
before closing the session. Closing wipes owned config bytes and best-effort
overwrites and removes the session files. It is idempotent.

Abrupt process death can leave private plaintext staging. Startup cleanup runs
before an import or connection is allowed and removes those abandoned session
directories without following links. Cleanup failure is visible and prevents new
work until explicit recovery succeeds. Closing a session ends its native borrow
lease even if wiping fails, because callers must already have joined and destroyed
every native handle. The retained directory remains available for that recovery
to retry. A cleanup error takes precedence over a simultaneous validation error;
it cannot be hidden as a suppressed native failure. This is bounded cleanup,
not a claim that process death immediately erases plaintext. The store never
puts secret content into logs, exception messages,
Intents, saved state, preferences or the public catalog.

## Failure channels

`StoreException.reason` distinguishes invalid input, capacity limits, corrupt
data, unavailable keys, local I/O failure and missing IDs. Messages are fixed and
contain no peer-controlled text. Corrupt data, unavailable keys, local I/O errors
and conflicting session ownership latch the controller's storage failure until
an explicit successful recovery. Invalid input, capacity exhaustion and missing
IDs are ordinary refused operations. Explicit recovery first settles any old
native run and then retries abandoned-file cleanup. A newly observed native-stop
or session-cleanup failure ends that attempt; recovery requires another explicit
action. Cancellation remains the caller's lifecycle
responsibility. Store operations are synchronous and bounded and belong on an
I/O dispatcher. The importer passes its cancellation check to `beforePublish`,
which runs after the private ciphertext has been synced and immediately before
the atomic rename. A cancellation thrown by that check removes the candidate
and preserves the old snapshot. Cancellation can arrive between the check and
rename, or after rename. In those cases the complete new configuration may
already be committed. The importer must refresh actual catalog state when it
resumes rather than assume rollback. The cancellation check and rename are not
one atomic operation. This callback must not reenter the store or perform I/O.
One process owns the store. It is not an interprocess coordination API.

## Provider storage boundary

Provider enrollment uses the shared Android provider library's `ProviderStore`
and `ServiceController`. Those owners serialize enrollment epochs, immutable
record hashes, grant publication, revocation and transport deadlines. Ito supplies
`ItoProviderBackend` for encryption and `ItoProviderServices` for selection and
transient native sessions. Neither application depends on the other's APK, UI,
VPN service or private vault. Provider state never enters the manual catalog.

The backend's ciphertext lives in `noBackupFilesDir/ito-provider-records`; the
shared store's separate control files live in `ito-provider-state`. Both are
excluded from backups by the application policy. A separate non-exportable
AES-256 Android Keystore key, `ito.provider.records.v1`, encrypts provider
records with GCM and a 128-bit tag. The platform cipher generates each fresh
96-bit nonce. A format version, `ito/provider-storage/record/1` domain and
length-prefixed exact blob name are authenticated. Copying ciphertext to a
different provider record or
selection name fails authentication. This key and domain are independent of
the manual snapshot and YUME transport keys.

One record contains at most 1,052,672 plaintext bytes. Names, file counts, modes
and ciphertext reads are bounded. Directories are 0700, files 0600; links and
special files are refused. A write syncs its encrypted temporary file, atomically
replaces the named record and syncs its directory. A replacement authenticates
the previous record first. Before replacement, failure preserves the previous
record. Failure after replacement is ambiguous to the caller and cannot publish
Ready. The shared enrollment manifest remains the sole grant publication point.
Startup removes only backend-owned temporary ciphertext and shared provider
staging. It never promotes a temporary candidate.

Missing records return absence. Corrupt ciphertext, unavailable or missing keys,
and I/O failures throw fixed typed errors; they never become an empty enrollment
or a manual-selection fallback. Retained ciphertext prevents creating a new
key. Explicit local removal needs neither a key nor the network: the shared
store first durably invalidates the enrollment epoch and then removes only that
provider's encrypted records. It cannot restore a removed epoch. Remote
revocation can remain unknown. Removal preserves other providers, manual
configurations, routing preferences and any future local communication identity.
Flash erasure and JVM buffer wiping remain best effort.

`ItoProviderSessions` reuses `ConfigurationStore.stage` under its own
`noBackupFilesDir/ito-provider-runtime/ito-transport/sessions` root. It never
imports, selects or removes a manual configuration. Initialization explicitly
recovers abandoned provider staging before allowing provider work. The shared
validator owns the bundle format and provider bindings. `ItoProviderNative`
uses the public Ito JNI adapter to open the kit, parse the original and adapted
client configuration, and derive the fingerprint from actual private credentials.
It has no successful verifier default and creates no connection during validation.
Only referenced non-executable credential files are staged.

Fingerprint validation closes its session after the synchronous native call.
A connection keeps its `ItoProviderSession` until every native borrower joins
and all native handles close. Cleanup failure takes precedence, latches provider
staging unavailable and requires explicit successful recovery. Cancellation
preserves the thread's interrupt after cleanup. Process death may leave private
staging until startup recovery. Provider-native or storage failure cannot choose
a different server, manual configuration, provider or direct path. Account/API
deadlines and transport-lease deadlines remain separate shared-library owners.

## Call identity storage

`IdentityStore` seals the call core's snapshot of the local identity, its
contacts, pairing state and spent invitations in `noBackupFilesDir/ito-identity/snapshot.bin`.
It also retains the call core's admitted clock floor. Clock admission can
publish this checkpoint even if the subsequent invitation operation fails.
It does not change identity, contacts or spent records. No pending invitation
PSK or monotonic deadline is restored from this snapshot. The exact clock
rules and observation limits are in [calling security](https://github.com/FixCraft-Inc/ito/blob/main/docs/CALL_SECURITY.md).
The core owns the plaintext format and every trust and replay rule. The store
owns only sealing, publication and refusal. A separate non-exportable
AES-256 Keystore key, `ito.identity.v1`, encrypts it with GCM, a fresh
platform nonce and a 128-bit tag. The format version, the domain
`ito/identity-storage/1` and the record name are authenticated data. The
Ed25519 and identity-2 ML-DSA secrets are not hardware held: the core reads
them from the decrypted snapshot while it signs. Pairing codes, inbox secrets
and unconsumed pairing seeds receive the same encryption. Per-contact ratchets
and outbox plaintext use the independent content-key store in
[local content](LOCAL_CONTENT.md).

A publication authenticates the existing snapshot first, writes a private
temporary file, syncs it, renames it over the snapshot and syncs the
directory. A failure before the rename leaves the old snapshot and reports
not committed. A failure after it is ambiguous, and the core then refuses
further changes until the store is reopened. The contact book then shows the
storage failure instead of its last state. Opening the book again reopens
the durable snapshot once no call or message session still uses the store. Startup removes only
the named
temporary file. Corrupt or unauthenticated ciphertext is never replaced, and
a missing key is never recreated while ciphertext exists. The app shows the
failure and offers no reset. Recovery means clearing the app's data and
creating a new identity that contacts verify again.

The snapshot is excluded from backups with the rest of `noBackupFilesDir`.
It is independent of manual configurations, provider records and transport
keys, so removing a provider or a configuration keeps identity and contacts.
Plaintext copies in Kotlin are wiped after sealing. JVM and flash erasure
remain best effort.

The optional [application lock](APP_LOCK.md) gates new identity-store access
and native book operations. Its authenticated proof does not replace or
reconfigure `ito.identity.v1`. Existing authorized call borrowers may finish
while locked, and no new identity/contact mutation is allowed. Communication
messages, history and photos use the independent [local-content store](LOCAL_CONTENT.md),
whose random encryption key is wrapped by the application-access owner.

An invitation never enters this store's plaintext as a persisted secret
beyond the core's spent record. The controller passes the locally generated
invitation to the ratchet, then wipes its temporary bytes. The incoming owner
retains only the native authenticated handle until acceptance, refusal or
expiry. Neither screen state nor notification intents hold the invitation.
The scanner's luminance copy is wiped when the camera closes. Navigation
state saves only public contact codes, never an invitation. JVM strings
created for pairing and safety codes cannot be wiped.
